## 三 软件开发背景

**时间：0:00—0:45；屏幕：学生端首页。**

**现场讲述：**

> 老师好，我展示的项目是“校园汇——校园活动发布与报名管理平台”。
>
> 在校园生活中，讲座、社团和志愿活动的通知经常分散在群消息和海报里。学生需要来回查找信息，报名以后也不容易知道审核结果；组织者则需要手工整理名单和统计人数。
>
> 因此，我开发了这个应用，希望把活动发现、在线报名、管理员审核和结果查询放在同一个平台中，减少信息分散与重复统计的问题。

讲述时停留在首页，让老师看到导航、分类入口和活动卡片即可，不必立即逐个点击。

## 四 概要设计

**时间：0:45—1:25；屏幕：保持首页。**

**现场讲述：**

> 系统分为学生端和管理员端。学生端负责浏览、筛选活动、提交报名和查询个人记录；管理员端负责发布与维护活动、审核报名、查看用户和统计数据。
>
> 数据主要有用户、活动和报名记录三类。报名记录通过用户编号和活动编号，把学生与活动关联起来。
>
> 代码按页面组件、业务服务和存储工具分层。页面负责展示，服务层统一校验业务规则，存储层负责保存数据，使不同页面遵循相同规则。

**理解与答辩参考，不逐字朗读：**

```text
学生端 / 管理员端页面
          ↓
React Router 路由与角色守卫
          ↓
Context 共享状态与统一操作入口
          ↓
platform.js 业务服务与权限检查
          ↓
storage.js → 浏览器 localStorage
```

| 数据实体 | 主要内容 | 关联方式 |
| --- | --- | --- |
| User 用户 | 账号、姓名、角色、联系方式、学院 | 一个用户可以有多条报名记录 |
| Event 活动 | 标题、分类、时间、地点、容量、发布状态 | 一个活动可以有多条报名记录 |
| Registration 报名 | 用户编号、活动编号、提交时间、审核状态、备注 | 将学生与活动联系起来 |

这不是已经部署的前后端分离系统。当前业务和数据都在浏览器内运行，Node.js 主要用于开发、构建及测试工具。

## 五 关键技术

**时间：1:25—2:20；屏幕：保持首页。**

**现场讲述：**

> 技术上，我使用 React 构建组件，用 React Router 组织学生端和管理端路由；通过 Context 共享用户与业务数据，配合 CSS 实现桌面和手机布局。
>
> 关键业务规则集中在服务层。例如待审核和已通过都占用名额，重复报名会被拦截，活动截止或满额后不能报名。页面显示与提交时的校验都使用统一规则。
>
> 数据用 localStorage 持久化，刷新后仍能保留；ECharts 根据活动和报名记录计算图表。密码使用加盐 PBKDF2 派生值保存，避免直接存储明文。不过，这仍是本地前端原型，正式上线还需要后端认证、权限校验和数据库。

**关键技术与源码对照，供老师提问时使用：**

| 技术或设计 | 在本项目中的实际作用 | 代表文件 |
| --- | --- | --- |
| React 组件化 | 复用活动卡片、状态标签、确认弹窗、分页等界面 | `src/components/UI.jsx` |
| React Router | 页面跳转、嵌套路由、登录与角色守卫 | `src/App.jsx` |
| Context 与 Hooks | 共享数据与会话，操作完成后更新界面 | `src/context/AppContext.jsx` |
| 集中业务规则 | 登录权限、活动状态、重复报名、容量和审核校验 | `src/services/platform.js` |
| localStorage | 按键存储用户、活动、报名及会话；处理读取异常 | `src/utils/storage.js` |
| ECharts | 分类分布、报名趋势、热门活动等数据可视化 | `src/components/Analytics.jsx` |
| Web Crypto | PBKDF2、SHA-256，100000 次迭代派生密码值 | `src/services/platform.js` |
| CSS 响应式布局 | 窄屏导航、卡片排布、表格横向滚动 | `src/styles/global.css` |
| Vite | 开发服务器与生产构建 | `vite.config.js` |
| Node Test 与 Playwright | 验证业务规则与浏览器中的完整操作流程 | `tests/` |

不要把密码派生称为“可解密的密码加密”，也不要把前端角色检查称为可靠的生产级权限控制。用户仍可通过开发者工具修改本地数据。

**预期结果：** 报名状态为待审核；“立即报名”变成报名状态提示与“查看我的报名”入口。

**预期结果：** 下载文件名为“校园汇-报名记录.csv”；统计图表正常显示，周期可以切换。

统计口径说明：活动总数含草稿、不含已删除活动；报名总记录数含取消和拒绝记录；热门活动按待审核与已通过人数合计排序。不要把“报名总记录数”直接称为去重后的学生人数，也不要说通过审核会让报名总数增加。

**时间：6:45—7:20；身份：管理员切换为学生。**

**操作：**

2. 用“学生账号”快捷填入并点击“登录”。
3. 点击顶部“我的报名”。
4. 切换“已通过”标签，找到“校园 Web 开发交流会”。
5. 指出该条报名的“已通过”状态与审核时间。保留结果页面作为结束画面。

**现场讲述：**

> 学生再次进入我的报名，就能看到审核已通过以及审核时间。至此，同一场活动从发布、被发现、提交申请，到管理员审核和学生查询结果，完成了完整流程。

**预期结果：** 学生看到的是刚才管理员处理的同一条记录，不是另一条预置报名。

## 八 备用功能展示

以下内容用于老师追问或单独排练。正式计时超出计划时直接跳过，不要打断主线。

### 1 取消报名与名额释放

1. 用 `20260001` 登录，进入“我的报名”，找到刚才的已通过记录。
2. 点击该记录的“取消报名”，在弹窗点击“确认取消报名”。
3. 切换“已取消”标签，展示记录被保留。
4. 打开同一活动详情，人数从 `1 / 50` 变为 `0 / 50`；在其他人没有报名的前提下，剩余名额恢复 50。

讲述：“活动开始前，学生可以取消本人有效报名。取消后释放名额，但保留历史记录；若仍在报名期且有名额，可重新申请。”

这一步应放在主线审核结果展示之后，否则管理员无法再审核已经取消的申请。

### 2 拒绝报名与审核备注

1. 先让学生对尚可报名的活动提交一条新申请。
2. 管理员进入“报名管理”，定位这条待审核记录。
3. 点击“拒绝”，在“审核备注”填写“请完善报名资料后重新申请”，点击“确认拒绝”。
4. 切回同一学生，在“我的报名 → 未通过”中查看原因。

讲述：“拒绝也会释放名额，学生能看到处理状态和备注。当前实现允许拒绝后重新申请。”

### 3 满额、草稿与截止状态

1. 如果刚恢复了当天演示数据，在活动广场搜索“星空”，打开“星空之下，探索宇宙的边界”。它的容量为 2，预置两条有效报名，显示名额已满。
2. 在管理员“活动管理”筛选“草稿”，能找到“设计思维与校园生活”；退出管理员后，学生公开列表中不显示该草稿。
3. 对于已截止、进行中和已结束的活动，展示禁用的报名按钮即可，不需要修改系统时间。

讲述：“活动状态综合发布时间设置、实际时间和有效报名人数计算，避免只靠手动标签判断。”

如果没有恢复数据，预置活动可能已经结束，不应仍声称“星空”活动一定显示已满。

### 4 编辑、下架与逻辑删除

1. 管理员进入“活动管理”，搜索演示活动。
2. 点击编辑图标，修改活动地点，点击“保存修改”，再查看详情确认更新。
3. 若活动仍未截止，点击“下架 → 确认下架”；学生仍可查看详情，但无法新增报名。
4. 在管理列表点击“发布 → 确认发布”，恢复报名。
5. 删除放在所有演示结束之后：点击删除图标和“确认删除”。活动从公开与管理列表移除，已有报名仍作为历史保留，不再允许审核。

讲述：“下架用于暂停新增报名，逻辑删除则保留历史关系，避免删除活动时把报名记录一并丢失。”

不要在主线报名、审核之间删除演示活动。

### 5 注册与个人资料

1. 退出登录，点击“登录 / 注册 → 注册学生账号”。
2. 填写一个从未注册过的账号、姓名和两次一致的密码，点击“注册并开始探索”。
3. 进入“个人中心”，修改学院或演示联系电话，点击“保存资料”，刷新确认保存。

讲述：“注册检查账号唯一性和表单格式，新注册账号只能是学生；个人资料修改后同样持久化。”

为避免排练时账号重复，可依次使用 `demo_student01`、`demo_student02`。

### 6 用户查询与角色限制

1. 管理员进入“用户管理”，搜索 `20260001`，再切换学生或管理员角色筛选。
2. 切换到学生账号后，在地址栏输入同一站点下的 `/admin`。
3. 展示“当前账号没有访问权限”，点击“返回我的首页”。

讲述：“路由层拦截错误角色，服务层还会再次检查操作身份。用户管理当前提供查询和状态展示，不包含管理员手动禁用账号的操作。”

### 7 手机布局

1. 在桌面浏览器缩窄窗口，或用开发者工具切换到约 390 像素宽度。
2. 展示折叠菜单、双列活动卡片和详情页的单列布局。

讲述：“布局使用 CSS 媒体查询适配窄屏。这里演示的是响应式布局，不表示手机能访问电脑浏览器中的本地报名数据。”

## 九 常见问题与回答参考

**问题：有没有后端，数据保存在哪里？**

答：当前是纯前端课程原型，用户、活动、报名和当前会话保存在浏览器 localStorage。开发用的 Vite 服务提供页面与资源，不是业务后端。刷新可以保留数据，但不同设备不会共享。

**问题：为什么待审核也要占名额？**

答：如果只计算审核通过的人数，很多待审申请可能同时超过容量。当前统一让待审核和已通过占位，拒绝或取消释放名额，因此审核通过不会重复占位。这是单浏览器规则；正式系统还需服务器事务或原子操作控制并发。

**问题：如何判断活动还能不能报名？**

答：先检查活动是否被删除或仍为草稿，再结合结束时间、开始时间、截止时间、下架状态和有效报名人数判断。提交时重新校验，而不是只看页面按钮是否可点击。

**问题：如何更新页面和数据？**

答：操作通过统一业务服务写入本地存储，再刷新 Context 共享状态。其他同源标签页的存储变化通过 storage 事件触发更新；页面每 30 秒更新用于状态判断的当前时间。它不是服务器推送，也不是跨设备实时同步。

**问题：密码处理是否安全？**

答：演示版本使用带盐值的 PBKDF2-SHA-256 派生值保存密码，没有直接保存明文密码。但角色和数据仍可在浏览器中被修改，不能据此宣称具备生产级认证安全。真实系统应将认证、密码存储与最终权限校验放到后端。

**问题：图表数字是否写死？**

答：初始化的是演示活动和报名记录，图表中的数量、比例、时间趋势与排行由这些实体计算，并随新增、审核等操作变化。活动总数、报名记录数和有效报名人数有不同的统计口径。

**问题：删除为什么不直接把数据清掉？**

答：活动采用 deleted 标记。这样可以从列表中隐藏活动，同时保留用户历史报名和统计依据。界面没有单条活动恢复入口，删除前会要求确认。

**问题：项目如何测试？**

答：项目提供 Node 业务测试，覆盖权限、重复报名、容量、审核取消、数据持久化等规则；还提供 Playwright 浏览器测试，覆盖学生报名与管理员审核、发布编辑删除、注册和移动布局等流程。需要现场展示测试结果时，应在演示前实际运行 `npm.cmd test` 和 `npm.cmd run test:e2e`，以本次运行结果为准。

**问题：以后如何扩展？**

答：优先将集中服务层对本地存储的调用替换为后端 API，并增加数据库、服务端认证和权限检查。在共享数据与并发规则可靠之后，再加入通知、签到或活动评价等功能。
